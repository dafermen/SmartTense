# SmartTense Developer Guide

This guide explains how the source code is organized and how to work on the app safely.

## Architecture

SmartTense is intentionally small. Most behavior is split into these areas:

- `src/App.jsx`: React state, page composition, controls, import/export, Settings data manager, and rendering.
- `src/conjugation.js`: grammar engine that generates sentence rows.
- `src/learningContentAdmin.js`: pure helpers for learning-content cloning, export payloads, and Settings summaries.
- `src/learningDiagnostic.js`: pure helpers and labels for the local CEFR self-check.
- `src/learnerLanguages/`: learner-language translations, usage notes, and explanations.
- `src/data/`: default data, tense metadata, and JSON validation.
- `src/styles.css`: responsive layout for Home, Theory, Practice, Individual, Complete, Production, Settings, mobile cards, and shared controls.
- `src/GuidedLessonPage.jsx` and `src/guidedLesson.js`: mobile lesson player and pure step-building/scoring helpers.
- `src/guidedLesson.css`: isolated responsive styles for the one-activity-at-a-time lesson.
- `src/data/contentQuality.js`: reusable A1/A2 content audit for options, contexts and methodology coverage.

The app loads editable verb data from `public/data/verbs.json`. If that request fails, it uses the embedded `DEFAULT_DATA` from `src/data/defaultData.js` so the UI can still run.

The project also has the first learning-content data source in `public/data/learningUnits.json`. Theory and Practice render this content as compact guided-learning surfaces. Validate learning content with `src/data/learningContentValidation.js`.

## Main UI Surfaces

### Home

Home is a compact dashboard. It uses existing generated data and does not introduce new grammar rules.

Home includes:

- Current verb summary.
- Quick actions to Theory, Individual, Production, Complete, and Settings.
- CEFR route filter for All, A1, A2, B1, and B2.
- One affirmative preview row generated by `buildRows`.
- Local progress based on visited verb IDs.
- Recommended next learning step based on unit progress.
- Local CEFR diagnostic with a suggested starting unit.

### Theory

Theory renders the primary learning unit from `public/data/learningUnits.json`. It is intentionally read-only in this phase.

Theory includes:

- objectives;
- linked tenses and context tags;
- short explanation;
- signal words;
- structures;
- common mistakes;
- contextual examples;
- context vocabulary;
- starter practice preview.

Do not add answer checking or scoring here. Interactive practice belongs to Practice.

Theory uses `src/learningContexts.js` to filter examples and vocabulary by the selected context.

### Guided Lesson

Guided Lesson is available when the active unit defines `productionTask`. All four A2 units build their sequence with `buildGuidedLessonSteps` and reuse exercises from the unit's existing `exercises` section. Do not copy those exercises into another collection.

The player keeps its draft state locally, shows one step at a time, requires answer checking before continuing past guided questions, and returns to Theory or Practice without adding a new main-menu destination.

### Explanations

Generated rows include an `explanations` object for each form:

- `affirmative`
- `negative`
- `questionPositive`
- `questionNegative`

Each explanation includes a pattern, reason, subject, auxiliary, verb form, and short note. The UI renders these inside the compact `Why this form?` panel used by Complete, mobile cards, and Individual.

Keep explanations concise. They should explain the existing generated row; they should not create a separate grammar engine.

### Practice

Practice renders starter exercises from the active learning unit. It uses `src/practice.js` for answer extraction, normalization, and scoring.

Current MVP behavior:

- reads `exercises` sections from `public/data/learningUnits.json`;
- filters exercises by selected context;
- renders dropdown answers; A1/A2 options are curated in the content source;
- checks answers locally;
- shows immediate correct/try-again feedback;
- resets the current browser-session practice draft.

Speaking/writing flows now live in Production.

### Production

Production is the speaking and writing workspace with local revision tracking.

Current MVP behavior:

- prompts loaded from `src/data/productionPrompts.js` with mode and tense metadata;
- prompts include `cefrLevel` and `unitIds` so Production can suggest tasks for the active unit;
- composer can show suggested prompts or all prompts;
- compose answers with optional self-review notes;
- local status tracking (`draft`, `done`, `needsReview`, `approved`);
- filters for mode and status on the attempt queue;
- one-row edit/update and delete confirmation.

Attempts are stored in local app state and persisted in local settings.

Keep the attempt queue global unless a product phase explicitly changes it. Suggested prompts should guide the composer without hiding existing attempts.

### Contexts And Vocabulary

Context helpers live in `src/learningContexts.js`.

Current responsibilities:

- map unit `contextTags` to the root `contexts` catalog;
- filter examples, vocabulary, and exercises by selected context;
- expose vocabulary cards from `vocabulary` sections.

Keep this layer data-focused. Do not put grammar-generation rules or Settings authoring behavior here.

### Learning Path

The learning path is local and unit-based. `src/learningPath.js` owns the pure helpers for:

- filtering units by CEFR level;
- deriving unit status;
- recommending the next step;
- marking unit progress;
- resetting one unit.

The current flow is Home -> Theory -> Guided Lesson -> Practice -> Production. Individual remains a focused affirmative practice surface and can be opened on demand.
Home shows the recommended next step, and Settings can reset the current unit progress.

### Level Diagnostic

The level diagnostic is local and self-assessed. `src/learningDiagnostic.js` owns:

- the four CEFR checks shown in Home;
- result calculation from checked items;
- toggling answer state.

`App.jsx` stores `diagnosticAnswers` with the rest of local settings. Home can apply the suggested unit, and Settings can reset the diagnostic. Update `tests/learningDiagnostic.test.js` when changing result rules or check IDs.

### Learning Content Administration

Settings includes a compact learning-content manager for the current browser session.

Current MVP behavior:

- imports compatible `learningUnits` JSON as a draft;
- validates the draft with `validateLearningContent`;
- previews units, contexts, vocabulary, and exercise counts;
- applies the draft to Theory and Practice after confirmation;
- exports the draft for source-control updates.

Do not add a large visual authoring studio inside `App.jsx`. If editing forms for units or exercises become necessary, extract focused helpers/components first and keep validation as the gate before applying content.

### Individual

Individual is affirmative-only practice. It builds rows from selected subjects and selected Individual tenses. Tense and subject controls are multi-select; group labels toggle entire groups.

This view should remain visually focused. Do not add negative or interrogative forms here unless the product decision changes.

### Complete

Complete renders the full conjugation table. Users can toggle visible sentence-form columns while the row data remains unchanged. Subject and Tense columns are sticky on desktop for easier comparison.

## Main Data Flow

1. `App.jsx` loads verb data with `fetch('/data/verbs.json')`.
2. `validateVerbData` checks the JSON shape before state is updated.
3. Learning-content JSON is loaded from `public/data/learningUnits.json` and validated by `validateLearningContent`.
4. The selected verb, search text, verb pattern, subject, level, tense group, page, draft content, and display preferences are stored in React state.
5. Search and pattern filtering reduce the verb list shown in selectors and recommendations.
6. `getVerbSummary` and `classifyVerbPattern` power the verb profile and pattern filter.
7. `getTensesByGroup` filters visible Complete tenses by group and learning level.
8. `buildRows` generates affirmative, negative, interrogative, and negative interrogative sentences.
9. `src/learnerLanguages/` adds learner-language translations and usage notes.
10. `buildRows` attaches `explanations` for each generated sentence form.
11. The same row model is reused in Home preview, Individual, and Complete views.
12. `Practice` uses `getPracticeExercises` and `scorePracticeAnswer` for local answer checks.
13. `src/learningContexts.js` maps contexts and filters examples, vocabulary, and exercises.
14. `learningPath` derives unit progress and Home recommendation.
15. `src/learningDiagnostic.js` derives the local CEFR diagnostic result.
16. `src/data/productionPrompts.js` provides starter speaking/writing prompts with CEFR/unit metadata.
17. `Production` maintains per-prompt attempts in local app state with status and filters.

## Important Source Files

### `src/App.jsx`

Owns user interaction and page rendering. This file should stay focused on state and UI composition, not grammar rules.

Key responsibilities:

- Load default JSON data.
- Handle imports and exports, including client-side file checks before import.
- Track filters, page selection, visible Complete columns, and Individual selections.
- Keep interface language and learner language as separate settings.
- Render Home, Theory, Practice, Individual, Production, Complete, Settings, Documentation, and About.

### `src/conjugation.js`

Owns sentence generation. Add or adjust tense behavior here.

Important functions:

- `buildRows`: returns table-ready row objects.
- `buildFormExplanation`: builds concise explanation metadata for one sentence form.
- `getTensesByGroup`: applies learning level and tense group filters.
- `conjugateRegular`: handles normal verbs.
- `conjugateBe`: handles `to be`, because it does not follow normal auxiliary rules.
- `conjugateModal`, `conjugateCan`, `conjugateShould`: handle modal-style examples.
- `classifyVerbPattern`: classifies principal verb forms as `AAA`, `ABB`, `ABC`, `ABA`, or `REGULAR_ED`.

### `src/learnerLanguages/`

Owns explanations for the student's first language. The English grammar engine should not contain Spanish, French, or other learner-language rules directly.

Current files:

- `index.js`: registry of supported learner languages.
- `es.js`: Spanish translations, Spanish subject labels, and Spanish usage notes.
- `fr.js`: French translations, French subject labels, and French usage notes.

To add another learner language later, create a language module with the same methods as `es.js`, register it in `index.js`, and add tests for its sentence translations and usage notes.

### `src/data/defaultData.js`

Contains built-in verbs, subject metadata, tense definitions, and learning levels.

### `src/data/validation.js`

Protects the app from invalid imported JSON. Validation intentionally rejects oversized collections, unknown fields, unsupported schema versions, unsafe IDs, markup-like strings, and fields that exceed length limits.

### `src/data/learningContentValidation.js`

Protects structured learning content. It validates learning units, section types, grammar structures, common mistakes, examples, exercises, vocabulary, duplicate IDs, unsupported schema versions, and markup-like strings.

It also validates the root `contexts` catalog and rejects examples, exercises, vocabulary, or unit tags that reference an unknown context.

### `src/learningContexts.js`

Owns context filtering helpers for learning content. It does not own UI state; `App.jsx` stores the selected context and passes it to Theory and Practice.

### `src/learningContentAdmin.js`

Owns pure helper logic for the Settings learning-content manager:

- `cloneLearningContent`
- `buildLearningContentPayload`
- `getLearningContentSummary`

Keep these helpers independent from React so they can be tested directly.

### `src/data/productionPrompts.js`

Holds the local starter prompts used in Production.

- prompt entries with `id`, `mode`, `tenseId`, `title`, `prompt`, `rubric`, and `suggestedTimeMinutes`;
- constant `PRODUCTION_STATUSES`;
- no persistence or network calls in this file.

Update `tests/productionPrompts.test.js` when prompt shape, supported statuses, or tense links change.

### `public/data/learningUnits.json`

Stores learning units as data. The first unit is `present-simple-foundation`, which includes:

- objectives;
- short theory;
- structures;
- common mistakes;
- contextual examples;
- context vocabulary;
- starter exercises.

This file is the bridge between the current conjugation trainer and the guided learning experience. Theory and Practice use it now.

Schema version 3 adds curriculum metadata:

- `cefrLevel`: course level (`A1`, `A2`, `B1`, `B2`);
- `unitOrder`: recommended order inside the CEFR level;
- `prerequisiteUnitIds`: unit IDs that should be completed first.

Keep `level` for the existing internal difficulty filter (`basic`, `intermediate`, `advanced`). Do not replace it with `cefrLevel`; they serve different purposes.

## Testing Guidance

Add tests when changing:

- Conjugation output.
- Form explanations.
- Practice answer normalization and scoring.
- Context filtering and vocabulary extraction.
- Learning-content admin summaries and export payloads.
- Learning path recommendations and unit progress updates.
- Learning level filtering.
- JSON validation.
- Learning content validation.
- Learner-language translations or usage notes.
- Import/export behavior that can be isolated from the browser.

The current automated tests focus on the grammar engine and JSON validation because those areas are easiest to regress silently. For critical UI/navigation changes and phase milestones, run `npm run release:check`.

Recommended responsive checks:

- Desktop: 1280px wide.
- Mobile: around 390px wide.
- Confirm no horizontal overflow.
- Confirm buttons remain at touch-friendly size.
- Confirm Home, Theory, Practice, Individual, and Complete remain readable with several selected filters.
- For phase milestones, follow `docs/RELEASE_CHECKLIST.md`.

## Adding A Tense

1. Add the tense entry to `TENSES` in `src/data/defaultData.js`.
2. Add the generation template in `src/conjugation.js` for regular verbs.
3. Check whether `be`, `can`, or `should` need custom handling.
4. Add or update tests in `tests/conjugation.test.js`.
5. If the tense should appear in Individual, update `INDIVIDUAL_TENSE_GROUPS` in `src/App.jsx`.
6. Update user-facing documentation if the learning flow changes.

## Adding A Verb

For built-in data, update both files:

- `public/data/verbs.json`
- `src/data/defaultData.js`

Keeping both in sync preserves fallback behavior.

For temporary user testing, use Settings -> Import JSON, Settings -> Edit on one row, or Settings -> Bulk edit in the app. The Settings data table is indexed, searchable, sortable, and paginated; single-row edits keep a backup so Cancel can restore the row before saving.

See `docs/DATA_SCHEMA.md` for the accepted fields.

Verb pattern classification is calculated from `base`, `past`, and `participle`. Do not store `AAA`, `ABB`, or `ABC` manually unless the data model changes later.

## Adding Learning Content

Learning content lives in `public/data/learningUnits.json`.

Before changing A1 or A2 content, run `npm run audit:content`. Errors block ambiguous answer data; warnings identify generated options, incomplete context coverage, missing exercise kinds, or methodology blocks that have not been activated yet.

The one-time Phase 21 authoring migration lives in `scripts/curate-a1-a2-content.cjs`. It is idempotent and documents the curated distractors and context additions used to produce the current JSON.

The Phase 23 migration lives in `scripts/complete-a2-practice.cjs`. It is also idempotent and ensures every A2 unit covers fillBlank, transform, chooseTense, correctMistake, and translation.

1. Add one small unit at a time.
2. Use a unique hyphenated `id`.
3. Link `tenseIds` to existing tense IDs from `src/data/defaultData.js`.
4. Keep theory short and example-driven.
5. Add context metadata when examples, vocabulary, or exercises should be filterable.
6. Add or update tests in `tests/learningContentValidation.test.js` when the schema changes.
7. Update `docs/LEARNING_CONTENT_SCHEMA.md`.
8. Check Theory and Practice after adding sections that should be visible to learners.

Run:

```bash
npm test
```

The validator rejects unknown fields, unsafe strings, unsupported section types, unsupported exercise kinds, duplicate IDs, and oversized collections.

## Updating Practice

Practice is intentionally simple.

1. Add exercises to `public/data/learningUnits.json`.
2. Add `context` when an exercise belongs to one learning context.
3. Keep each answer exact and learner-readable.
4. Update `src/practice.js` only when extraction, filtering, or scoring rules must change.
5. Add or update tests in `tests/practice.test.js`.
6. Keep UI feedback immediate and local.

## Updating Contexts And Vocabulary

1. Add context catalog entries at the root of `public/data/learningUnits.json`.
2. Reference those IDs from `unit.contextTags`.
3. Add `context` to examples, vocabulary items, and exercises when filtering should apply.
4. Update `tests/learningContexts.test.js` when helper behavior changes.
5. Keep import/export and authoring tools in the Settings content manager, not inside the context-filter helpers.

## Updating Learning Content Administration

1. Keep import/export local to the browser session.
2. Always validate with `validateLearningContent` before applying a draft.
3. Keep preview data derived through `src/learningContentAdmin.js`.
4. Update `tests/learningContentAdmin.test.js` when summary or export behavior changes.
5. Update user-facing docs when the Settings content workflow changes.

## Updating The Learning Path

Learning path state is stored with the existing browser settings under `unitProgress`.

Rules:

1. Keep progress local.
2. Do not add accounts or backend sync.
3. Update `tests/learningPath.test.js` when changing statuses or next-step rules.
4. Keep Home recommendations short and action-oriented.

## Security Notes

SmartTense is safest when published as a static site. Imported JSON is read only inside the user's browser and never writes to server files.

Before publishing, review:

- `SECURITY.md` for the security model and publishing checklist.
- `public/_headers` for static hosting security headers on hosts that support it.
- `src/data/validation.js` when adding new JSON fields.
- `src/data/learningContentValidation.js` when adding new learning-content fields.
- `docs/GITHUB_PAGES.md` for GitHub Pages, custom subdomains, and the Vite base path used by deployment.

If a new JSON field is added, update `ALLOWED_VERB_KEYS`, `DATA_MANAGER_FIELDS`, documentation, and validation tests in the same change.

If a new learning-content field is added, update the relevant allowed-key set, documentation, and validation tests in the same change.

## Guided Learning And Skill Mastery

Guided Lesson is built from existing unit content by `src/guidedLesson.js` and rendered one step at a time by `src/GuidedLessonPage.jsx`. Do not duplicate theory or practice data for this flow. A methodology-ready unit defines `learnerContext`, `pronunciationDrills`, and `productionTask` in `public/data/learningUnits.json`.

Skill progress is local browser state stored with the existing settings under `skillProgress`. `src/skillMastery.js` owns the stable catalog, exercise mapping, mastery update, streak, and review scheduling rules. Both Practice and Guided Lesson must call `recordExerciseResult` after a checked answer. When adding a unit, map its exercises to a stable skill and add a focused test.

## Adaptive Review

`src/adaptiveReview.js` builds a deterministic queue from existing exercises that have valid answer options. It prioritizes due and low-mastery skills, selects one item per skill before repeating, and limits a session to eight questions. `src/AdaptiveReviewPage.jsx` owns session-only UI state; persistent mastery remains in App.

Keep adaptive selection explainable. Do not add opaque scoring, random ordering, accounts, or server state without a separate product phase and migration plan.

## Mobile Primary Navigation

At widths up to 880px, `mobile-primary-nav` exposes four learner destinations: Home, Theory, Practice, and Review. The side menu remains the route to advanced tools. At widths up to 720px, Home hides redundant verb detail, preview, profile, and secondary statistics while preserving the active-unit selector, continue action, progress, recommendation, and diagnostic.

The mobile smoke test covers all 10 Guided Lesson units and Adaptive Review. Run:

```bash
npm run audit:content
npm test
npm run build
npm run test:e2e:mobile
```

The audit now reviews A1, A2, B1, and B2. The E2E viewport is `390x844` and checks the four-item mobile navigation, horizontal overflow, accessibility names, 500 synthetic verbs, and 25-row Settings pagination.

## Action-Oriented Home Architecture

`src/LearningHubPages.jsx` contains three presentation components: the mobile Home focus, Course, and Progress. `src/learningHub.css` hides the legacy dashboard grids at `720px` and below while preserving them on desktop.

Home derives its values from existing `unitProgress`, `skillProgress`, and ordered learning units. Course changes `cefrFilter` and `activeLearningUnitId` before opening Guided Lesson. Progress is read-only and delegates Review or Course navigation back to App. Do not duplicate progress state inside these components.

The four mobile destinations are Home, Course, Practice, and Progress. Theory and Guided Lesson are considered Course subpages; Adaptive Review is considered a Practice subpage.

## Learning Journey Persistence

`src/learningJourney.js` is the source of truth for resumable unit state. `journeyProgress` is persisted with the existing local settings and keyed by unit ID. Keep Guided Lesson, Focused Practice, and Production fields inside that unit object rather than introducing component-specific storage keys.

`getJourneyPercent` weights Guided Lesson at 60%, Practice at 30%, and Production at 10%. Production completion is detected after a saved attempt linked to the active unit; App then marks the journey complete, selects the next ordered unit, and returns Home.

`src/FocusedPracticePage.jsx` renders one exercise at a time and persists answers, results, and current index. `src/OnboardingDiagnostic.jsx` reuses `DIAGNOSTIC_CHECKS`; `diagnosticCompleted` controls whether onboarding is visible independently from temporary checkbox selections.

Course receives journey-derived statuses and disables units whose `prerequisiteUnitIds` are incomplete. Preserve this rule when changing the curriculum path.

## Interface Language And Visual System

Use `src/i18n.js` for every learner-facing interface label in Guided Lesson, Practice, Adaptive Review, Course, Progress, and Home. English learning content such as prompts and examples stays in the curriculum JSON; do not translate it as interface copy. Add important journey keys to `tests/uiLocalization.test.js` so both supported interface languages remain covered.

Atkinson Hyperlegible is bundled through `@fontsource/atkinson-hyperlegible` and imported in `src/styles.css`. Do not replace it with a network font. Reusable navigation and action icons belong in `src/UiIcon.jsx`; icons remain decorative when their adjacent text already provides the accessible name.

Keep motion short and purposeful. Every new animation must include a `prefers-reduced-motion: reduce` override. Avoid uppercase labels for full phrases, preserve readable secondary contrast, and use the completion celebration only for a real unit transition.



## Spanish Learner Guide Audit

Run `npm run audit:translations` after adding or changing verbs. The audit generates Spanish affirmative, negative, positive-question, and negative-question forms for Simple Present, Simple Past, and Simple Future across the complete public verb database. It also protects curated contextual meanings such as `catch the bus`, `hold a meeting`, `make a decision`, and `spend time`.

## Codex Session Continuity

Repository-level instructions live in `AGENTS.md`. The current implementation state, active phase, validation status, and next recommended tasks live in `docs/CURRENT_STATUS.md`. A new Codex session should read those two files before changing code, then use `docs/INDEX.md` for the complete documentation map.

Recent practice mistakes are stored in `skillProgress[skillId].mistakeExerciseIds`. Keep this inside the existing local progress payload. `recordExerciseResult` adds an incorrect exercise and removes it after a correct answer. `buildAdaptiveReviewQueue` gives these exercises the highest explainable priority.
